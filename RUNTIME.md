# Independent account runtime

The optional runtime keeps account credentials and native Device ID / Machine ID values separate, while managed Claude Code conversations share a stable working environment. It is an alpha feature for Windows and macOS. Linux supports the existing credential backend and CLI.

## Configure and launch

Install the tagged ccpick package first. You also need Node.js 22+, native Claude Code, and OpenSSL. Windows uses the OpenSSL executable included with Git for Windows; macOS uses `/usr/bin/openssl`.

Have your agent resolve the **native Claude executable**, rather than another ccpick wrapper or a shell script. Use `--native` and `--node` if automatic discovery finds the wrong program.

```sh
ccpick runtime setup --upstream-proxy http://127.0.0.1:8080 --dry-run
ccpick runtime setup --upstream-proxy http://127.0.0.1:8080
ccpick runtime add --email account@example.com
ccpick run
ccpick run -- --resume
```

The proxy address is an example. Supply your own loopback HTTP CONNECT proxy, without credentials in its URL. Proxy setup and routing belong to that service. ccpick rejects a missing proxy and does not connect directly when it fails.

Runtime setup writes only its own data directory. It does not replace the global `claude` command, copy old authentication, install a system certificate, or start desktop automatic switching. Existing unmanaged windows need to exit normally and be resumed with `ccpick run` to use this mode. ccpick does not close those windows for you.

Authorize each account through the official browser flow. The first account establishes the initial selection; later enrollment keeps your existing choice. Select a newly added account explicitly with `ccpick switch ACCOUNT`, or let the configured automatic policy choose it. Failed authorization leaves a placeholder for a later retry with `ccpick runtime login ACCOUNT`; it does not count as a usable account. Existing credentials remain in the old backend until you remove them through that backend yourself.

## Daily commands

```sh
ccpick accounts
ccpick usage --refresh
ccpick switch account@example.com
ccpick disable account@example.com
ccpick enable account@example.com
ccpick auto --dry-run
ccpick auto
ccpick runtime status
ccpick runtime doctor
```

You can identify an account by its generated profile name or enrolled email. `disable` makes it manual only: automatic selection skips it, while an explicit `switch` remains possible. The desktop menu marks it in purple. The runtime account store is separate from the old backend; optional legacy enrollment automation does not operate on this store.

To enable the existing tray/menu bar and predictive scheduler for runtime accounts, preview and run `ccpick setup --autoswitch`. Installing a package or configuring the runtime alone does not enable automatic decisions. Set `CCSWITCH_WATCH_ONLY=1` before desktop setup to monitor without switching.

Native `/login` inside a managed conversation registers the OAuth flow before opening the Chrome profile picker. Verified authorization is assigned to the matching account or a new profile. The login page runs in Chrome, whose network settings you must configure separately when its exit matters.

## What happens during a switch

```text
ccpick run / managed child
        → local authenticated TLS boundary
        → account snapshot: credential + account UUID + Device ID
        → user-configured CONNECT proxy
        → official supported Anthropic endpoint
```

One request takes one account snapshot. Selecting another account does not change a request already being streamed; later requests use the new account. The runtime keeps the native process and conversation history. It does not resubmit user messages or execute unfinished tools on its own. After a quota error, select an account and continue through Claude's normal prompt flow.

Automatic selection includes an expected account and selection generation. The service rejects a decision if another selection happened meanwhile. A manual-only target is checked again at the final mutation boundary. Unknown authorization or unavailable quota does not become a successful switch or zero usage.

## Conversation data and identity

The runtime uses a stable config directory for conversations and separate vault directories for accounts. Projects and file history share the existing local Claude transcript store. Arrow-key input history imports valid records and referenced paste-cache data with bounded reads, deduplication, native locking, and backups before replacement. Credentials and device identifiers are not imported from those history files.

Each account's identifiers are generated by native Claude initialization and verified before use. ccpick changes neither the operating-system identity nor the browser's fingerprint. An account on another computer gets that installation's native identifiers; this release does not provide an account export or cross-machine credential migration command.

The local API certificate and capability protect the runtime's loopback channel. Only managed processes receive the additional certificate trust. Account grants stay in individual vaults; local channel headers are stripped before upstream requests. Do not upload the runtime data directory, certificates, cache, logs, or account files to an issue.

## Supported boundary and verification

Supported paths include managed CLI conversations and their local child processes, normal Resume/Fork arguments, model requests, OAuth authorization, token refresh, account profile verification, and usage queries. Native support can change with Claude versions; keep the package current and check errors before continuing.

Hosted MCP authentication, voice, cloud sessions, remote control, and signed remote identities are outside the supported runtime paths. Ordinary tool downloads use the user-configured proxy and its routing policy. ccpick does not infer a residential route or manage a browser/VPN setup.

The test suite uses synthetic credentials, mocked native invocations, disposable homes, and local fake upstreams. It checks streams, identity coherence, callback routing, background settings, locks, stale decisions, and package privacy. These checks do not exercise a real user login or prove native compatibility on every machine.

`runtime doctor` checks local configuration; a configured proxy or selected account is not proof that a particular conversation has sent a successful request. To verify a real installation, finish one authorized login, inspect the intended browser route, launch a managed conversation, and confirm a normal reply. Test a real switch only within the user's requested scope.

## Troubleshooting

| Error | Next step |
| --- | --- |
| `runtime_not_configured` | Preview runtime setup with your proxy and native executable. |
| `upstream_proxy_unavailable` | Check the configured proxy service and routing; ccpick has no direct fallback. |
| `login_required` / `auth_unverified` | Finish official authorization for that account, then retry. |
| `selection_changed` | A newer choice superseded this automatic decision; keep the newer choice. |
| `identity_changed` / `wrong_account` | Stop using the affected profile and inspect the local account state; do not mix credential files. |
| `runtime_installation_conflict` | Existing runtime configuration differs; preserve its data and inspect before changing it. |
| Native Fork still rejects flags | Inspect flags explicitly supplied to that session. ccpick preserves them and does not remove native restrictions. |

To stop using runtime mode, stop launching conversations with `ccpick run`. Uninstall desktop integration with `ccpick uninstall` when requested; this retains account and history data. Preserve runtime data before any manual reconfiguration or removal.
